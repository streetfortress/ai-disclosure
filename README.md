# AI Disclosure

Streetfortress Industries uses agentic development heavily. Since mid-late 2025, most lines of code in our repositories have been generated by LLMs.

## What we promise

**Agents commit under their own identity.** Agent-authored changes are committed and signed as `sfi-agent`. Authorship in our repositories is data you can audit with git: `git log --author=sfi-agent`. We've found that when agent output 'masquerades' under a person's account, the review process gets unnecessarily complicated fast. A dedicated user account just makes sense in hindsight.

**Every change gets _at least_ eyes-on by a person.** Our mains are branch-guarded and the agent role has no merge or approve permission. This is enforced _on the repository by policy_, not with a prompt.

**Code review is a discipline and happens frequently.** Not every change needs a big review. But significant changes, often done to improve efficiency or add new features, definitely still do. Nothing about AI has changed that. We reassess and refactor changes frequently in the development process - the "one prompt gets it all" situations are somewhat uncommon.

**Changes are tested before they reach you.** We run a robust suite of CI, dev, and staging environments behind the scenes. Code changes are not accepted without passing tests and deployments only reach production after acceptance testing. This is not a claim that our software is perfect, just a statement about our stance on code quality.

**We'll hand write the "user facing surface", but we accept verbose LLM output in the comments and generated docs.** Look, we get it. A wall of LLM spam can suck to get hit with. But the best way we've found to keep docs in sync with the code is for agents to make doc revisions _along with the change_. Think about it: All of the context around the change is there in the model anyway, better to dump it out into docs where it doesn't disappear when the session ends.

To that end:
- READMEs, getting started material, guides, etc will be written by someone who uses and cares about the thing being written about.
- Technical reference docs, code comments, commit messages, PR descriptions, etc are all fair game to be 100% LLM generated.

We believe that if an idea is worth pursuing, it's worth talking about - so therefore if you can't be bothered to write about it, it's not worth a code change in the first place.

SFI is about ideas and building things. I never picked sides in the operating-system or text-editor wars, and we (SFI) are not enlisting in this one. Tools have changed; review, testing, and standing behind your work... these practices are not going anywhere.

## Why we publish authorship

In the spirit of _egoless programming_ and _blameless postmortems_, just as much as we don't care _how_ a code change was written, we really don't care _who_ it was written by. Changes are about taking ideas and implementing them: The intent and the direction of the change are accepted by the team (in code review). Asking *who* destroys the information flow; asking *what* improves the system.

There is a practical reason this matters more now: change volume. When changes can be produced faster than any one person can type, per-change ego has to go to zero or review turns adversarial. Reviewing intent and direction scales. Reviewing keystrokes does not.

## Contributions

AI-assisted contributions are welcome; disclose the assistance, and own what you submit — you're the one accepting intent and direction before we ever see it. Your change gets the same review as ours. Undisclosed machine-generated pull requests may be closed without ceremony.

The PR spam problem was never really about the tools, it was the careless nature of their use - just like any of the other "problem software" that's out there.
